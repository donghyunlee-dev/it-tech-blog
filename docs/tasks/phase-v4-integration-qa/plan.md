# plan — Phase V4 통합 QA

## 접근 방식

새 기능을 추가하는 작업이 아니므로 코드 변경을 먼저 계획하지 않는다. 대신 prd.md 기능 정의를 항목별 체크리스트로 바꾸고, 로컬 프로덕션 빌드(`npm run start`)를 실 Confluence 자격 증명(`.env`)에 연결한 상태로 띄워 하나씩 확인한다. 문제를 발견하면 그 즉시 최소 범위로 고치고 재검증한다.

## 점검 항목

1. **홈**: 게시 문서 목록, 태그 라인, 최근 댓글 사이드바.
2. **상세**: 본문 렌더링(컨버터), 태그, 관련 글, 구조화 데이터(JSON-LD), 댓글 섹션(목록 조회).
3. **SEO 엔드포인트**: `/sitemap.xml`, `/robots.txt`, `/rss.xml`이 실제 게시 문서를 반영하는지.
4. **리다이렉트**: 이전 태스크와 동일한 방식(실 UUID 재사용)으로 슬러그 이동 재확인, not-found 페이지 재확인.
5. **rate limiting**: 외부 사용자 경로에서 여전히 429가 걸리는지, 헤더 존재 확인.
6. **댓글 작성 흐름 통합 지점**: `/posts/[slug]`에 `?error=` 배너·리다이렉트·댓글 섹션이 동시에 존재해도 레이아웃/렌더링이 깨지지 않는지.
7. **Slack 알림 경로**: 실제 webhook을 울리지는 않되(운영 채널에 노이즈를 만들지 않기 위해), `sendSlackAlert` 호출 경로가 `SLACK_WEBHOOK_URL` 미설정 시 조용히 무시되는지 등 코드 경로를 확인.
8. **`/api/health/confluence`**: 실 Confluence 연동 상태 확인용 헬스체크가 정상 응답하는지.

## 검증 전략

- `npm run lint`, `npm run build`.
- 로컬 `npm run start`로 실 데이터 대상 curl/브라우저 점검(모두 읽기 전용 — 새 댓글이나 Confluence 쓰기는 만들지 않는다. 외부 사용자 댓글 작성 등 쓰기가 필요한 시나리오는 이미 이전 태스크에서 검증된 것으로 간주하고 재실행하지 않는다).
- 문제 발견 시 수정 후 동일 항목 재검증.

## 리스크

- Slack 알림처럼 "실패 시에만" 동작하는 경로는 실제 실패를 인위적으로 재현하기 어렵다 — 코드 리뷰로 갈음하고 실제 웹훅 호출은 생략한다(운영 채널 스팸 방지).
- 이번 QA에서 발견된 문제가 설계 변경급이면 이 태스크 범위에서 고치지 않고 별도 과제로 분리한다(스코프 통제 원칙).
