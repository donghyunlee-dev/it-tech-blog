# spec — 게시 주소 변경/삭제 시 리다이렉트 처리

## 문제 정의

prd.md/architecture.md의 SEO 기본 대응 요구사항("문서 주소가 변경되거나 삭제되면 기존 주소를 적절한 페이지로 연결한다")이 아직 구현되어 있지 않다. 현재 `src/app/posts/[slug]/page.tsx`는 slug가 일치하지 않으면 무조건 Next.js 기본 404를 띄운다.

data-spec.md는 공개 경로에 쓰이는 `publicSlug`가 `${작성자가 입력한 slug}-${Confluence 페이지 title(변경되지 않는 UUID)}` 형태이며, "URL에서 페이지를 역으로 찾을 때는 마지막 `-` 뒤 36자 UUID로 조회한다"고 이미 설계해 두었다 — 이번 작업은 이 설계를 실제로 구현하는 것이다.

## 두 가지 경로 구분

1. **주소 변경(사람이 읽는 slug 부분만 바뀜)**: 문서는 여전히 게시 중이고 페이지 UUID는 그대로다. 옛 URL의 UUID 접미사로 현재 게시 목록을 역조회하면 같은 문서를 찾을 수 있다 → 그 문서의 **현재** `publicSlug`로 308(영구 이동) 리다이렉트한다.
2. **삭제/게시 해제**: UUID로도 찾을 수 없거나 애초에 UUID 형식이 아닌 옛 URL. 이동할 대상이 없으므로 "적절한 페이지로 연결"은 잘 안내된 not-found 화면(사이트 헤더/푸터를 갖춘, 홈으로 돌아가는 링크가 있는 화면)을 의미하는 것으로 해석한다 — 현재는 프레임워크 기본 404만 뜬다.

## 범위 (In Scope)

- `src/lib/viewer/posts.ts`에 slug 재조회(UUID 역조회) 로직 추가.
- `src/app/posts/[slug]/page.tsx`가 "찾음/이동됨/없음/오류" 네 상태를 구분해 처리(이동됨은 308 리다이렉트).
- `src/app/posts/[slug]/not-found.tsx` 신규 — 사이트 헤더/푸터를 포함한 안내 화면(기존 `.empty-state` 스타일 재사용).
- `docs/product/prd.md`의 Phase V4 진행 상태 문구를 실제 코드 상태(Slack 알림은 이미 구현되어 있었음, 이번에 리다이렉트 추가, rate limiting은 별도 PR에서 완료)로 동기화.

## Out of Scope

- `GET /api/viewer/posts/{slug}`(JSON API)의 리다이렉트 처리 — prd.md가 이 기능을 "API 필요 여부: 아니오(Viewer 라우팅 내부 로직)"로 명시하고 있어 페이지 라우팅에만 적용한다.
- Editor 쪽에서 slug 변경 이력을 저장하는 기능 — Viewer는 Editor가 이미 계산해 둔 UUID 접미사만으로 역조회하며, 별도 이력 저장소를 두지 않는다.
- 통합 QA(Phase V4의 다른 항목) — 별도 과제로 남긴다.

## 수용 기준

- [ ] 게시 중인 문서의 slug가 바뀌었을 때, 옛 URL로 접근하면 새 URL로 308 리다이렉트된다.
- [ ] 실제로 삭제되었거나 게시 해제된 문서, 혹은 애초에 존재하지 않는 slug로 접근하면 사이트 헤더/푸터를 갖춘 안내 화면이 뜬다(프레임워크 기본 404 아님).
- [ ] `npm run lint`/`npm run build` 통과.

## 엣지 케이스

- UUID 접미사 패턴과 우연히 비슷하지만 실제로는 어떤 게시 문서와도 매치되지 않는 slug → not-found 안내 화면으로 처리(무한 리다이렉트 없음).
- 리다이렉트 대상 slug가 요청받은 slug와 동일한 경우(이론상 발생하지 않아야 하지만) → 안전하게 "찾음"으로 처리하고 리다이렉트하지 않는다.
