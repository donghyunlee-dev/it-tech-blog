# spec — 탭 간 `ax_pending_comment` 쿠키 충돌 완화

## 문제 정의

자체 코드 리뷰(2026-09-17, `docs/product/prd.md`) 3번 항목. `ax_pending_comment` 쿠키는 `path=/`로 브라우저 전체(같은 오리진의 모든 탭)에 공유되고, 어떤 AX Auth 왕복이 그 초안을 "소비"해야 하는지 구분할 방법(nonce/state 등)이 없다.

시나리오: 이미 로그인된 사용자가 Tab A에서 댓글을 저장하면(`ax_pending_comment` 설정 후 AX Auth로 리다이렉트) 그 왕복이 끝나기 전에, 같은 브라우저의 Tab B에서 (해당 시점에 세션이 아직 반영되지 않은 상태로) 평범한 "MS 계정으로 인증" 게이트 버튼을 누르면, Tab B의 콜백 요청이 Tab A가 남겨 둔 대기 중인 초안을 그대로 소비해 Tab A의 댓글 내용이 Tab B가 방금 인증한 계정으로 게시되고, 정작 Tab B는 로그인 세션이 생기지 않는다.

## 근본 제약과 현실적인 대응 범위

AX Auth의 로그인 시작 엔드포인트(`GET /auth/login/{clientId}`)는 `state`/nonce 같은 왕복 파라미터를 문서화하고 있지 않고(`login-integration-guide.md` 확인), `redirect_uri`는 사전 등록된 고정값이라 요청마다 다른 식별자를 실어 보낼 수 없다. 즉 "이 콜백이 정확히 어떤 왕복에 대한 응답인지"를 서버가 확실히 구분할 방법이 없다 — 완전한 근본 해결은 AX Auth 쪽에 state 파라미터 지원이 추가되어야 가능하며 이 저장소의 범위를 벗어난다.

따라서 이번 수정은 **가장 심각한 결과(엉뚱한 계정으로 잘못 게시됨)를 없애는 데 집중**하고, 잔여 위험(드문 동시 접근 시 대기 중이던 댓글이 조용히 유실될 수 있음 — 잘못된 계정으로 게시되지는 않음)은 감수하기로 한다.

## 범위 (In Scope)

- 평범한 로그인 트리거(게이트의 "MS 계정으로 인증" 버튼)가 시작될 때, 남아 있을 수 있는 `ax_pending_comment` 쿠키를 함께 지운다 — 그 결과 평범한 로그인 왕복은 절대로 다른 탭의 대기 중인 댓글을 소비하지 않는다.

## Out of Scope

- AX Auth 쪽에 state/nonce 파라미터 지원을 요청하는 것 — 이 저장소가 아니라 AX팀과의 연동 계약 변경이 필요하다.
- 동시에 발생하는 진짜 경쟁 상태(두 탭이 정확히 같은 순간에 각각의 쿠키를 쓰는 경우)까지 완전히 없애는 것 — 위 제약으로 불가능하며, 대신 실패 시 "엉뚱하게 게시됨"이 아니라 "조용히 유실됨"으로 완화하는 데 그친다.

## 수용 기준

- [ ] 게이트의 "MS 계정으로 인증" 버튼을 누르면 `ax_pending_comment` 쿠키가 항상 지워진 상태로 AX Auth에 리다이렉트된다.
- [ ] 댓글 저장 흐름(`postComment`의 리다이렉트 분기)은 기존과 동일하게 동작한다(자기 자신의 새 초안으로 쿠키를 덮어쓰므로 별도 처리 불필요).
- [ ] `npm run lint`/`npm run build` 통과.
