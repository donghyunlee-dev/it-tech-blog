# 디자인 방향성 — 에디토리얼 매거진형

## 왜 이 문서가 필요한가

[design-benchmark.md](design-benchmark.md)에서 목록/검색/댓글의 "구조"를 벤치마킹했고, 그 결과로 만든 [mockups/blog-ui-benchmark.html](mockups/blog-ui-benchmark.html)은 기능적으로는 맞지만 **어느 회사 블로그에 붙여도 어색하지 않을 만큼 중립적**이었다. 카드 그리드에 레드 배지 하나 얹은 정도로는 "이 블로그만의 성격"이 드러나지 않는다.

이 문서는 구조가 아니라 **성격(personality)**을 정의한다 — 상단/하단 구성, 리스트·상세 페이지에서 반복적으로 등장해 "이건 우리 매체다"를 각인시키는 시그니처 요소를 정한다.

- 관련 문서: [design-system.md](design-system.md)(토큰), [design-benchmark.md](design-benchmark.md)(기능 구조 벤치마킹), [../product/prd.md](../product/prd.md)(화면 정의)
- 목업 파일: [mockups/blog-editorial-direction.html](mockups/blog-editorial-direction.html)

## 선택한 방향: 에디토리얼 매거진형

세 가지 후보(A. 에디토리얼 매거진형 / B. 테크 노트형 / C. 따뜻한 사내 매거진형) 중 **A. 에디토리얼 매거진형**을 선택했다. 잡지/신문의 편집 언어(마스트헤드, 키커, 1면 기사)를 빌려와 "발행 주체가 있는 매체"라는 인상을 준다. `design-system.md`가 이미 정의한 "컨설팅 페이퍼처럼 정돈된" 톤, 화이트 캔버스+레드 포인트 위에 이 언어를 얹는다.

## 이미지 없이도 성립하는 디자인인가 (2026-09-15 검토)

**문제 제기**: 이 디자인은 히어로·카드·상세 페이지 전부 큰 이미지를 전제로 시작했다. 그런데 `data-spec.md`의 Publish Metadata에는 대표 이미지/썸네일 필드가 없고, Editor의 "이미지 등록" 기능도 본문 삽입용일 뿐 대표 이미지 지정 기능이 아니다 — 즉 실제로는 대부분의 글에 이미지가 없을 것이다.

**조사**: 브런치(brunch.co.kr)와 벨로그(velog.io)를 실제로 열어봤다.
- 브런치는 작가가 매 글마다 커버 아트를 직접 큐레이션하는 문학/에세이 플랫폼이라 오히려 이미지 의존도가 더 높다 — 우리 케이스의 반례에 가깝다.
- **벨로그**(국내 개발자 블로그 1위, 우리와 같은 장르)는 정반대였다. 트렌딩 페이지의 카드 중 썸네일이 아예 없는 텍스트 전용 카드가 이미지 카드와 같은 그리드에 자연스럽게 섞여 있었고, 실제 활동 중인 개발자 계정(153개 글)의 목록 화면에서는 화면에 보이는 게시글 제목 15개 중 이미지가 4개뿐이었다(로고·아바타 포함). **기술 블로그 장르에서는 텍스트 전용이 오히려 표준**이다.

**결론 및 반영**: 이미지를 "필수 조건"에서 "있으면 쓰는 보너스"로 낮췄다. 아래 시그니처 요소 목록의 ③⑤가 이 결정을 반영한 것이다 — 히어로는 사진 대신 타이포그래피+색 배경으로 무게를 주고, 카드 그리드는 텍스트 전용을 기본값으로 하되 본문에 실제 이미지가 있는 글만 선택적으로 썸네일을 붙인다(벨로그와 동일한 방식). 연재물의 경우 이미지 히어로 대신 벨로그의 "시리즈" 위젯(진행률+이전/다음)을 가져와 쓴다 — Editor 쪽에 새 기능을 요청하지 않고도 지금 데이터 구조만으로 완성도 있게 만들 수 있는 방향이다.

## 시그니처 요소 (반복 등장 — 이것이 "뚜렷한 느낌"을 만든다)

아래 5가지는 목록/상세/사이드바 어디서든 일관되게 반복되어야 한다. 산발적 장식이 아니라 **하나의 언어**로 기능해야 한다. 사진은 이 목록에 없다 — 있으면 좋지만 없어도 이 5가지만으로 정체성이 성립해야 한다.

1. **키커(kicker) 라벨**: 모든 제목 위에 카테고리를 작은 대문자 레드 텍스트로 얹는다(예: `BACKEND`). 배지(pill)가 아니라 제목과 한 세트로 읽히는 타이포그래피 요소 — 목록 카드, 히어로, 상세 페이지 전부 동일하게 적용.
2. **마스트헤드 밑줄**: 로고 아래 얇은 레드 룰(rule) 한 줄. 신문 마스트헤드에서 따온 절제된 시그니처.
3. **히어로(1면 기사)**: 홈 화면 최상단에 최신/대표 글 1건을 배치하되, **사진이 아니라 크기와 배경으로 무게를 준다** — 옅은 레드 틴트 배경 패널 + 굵은 레드 왼쪽 보더 + 훨씬 큰 타이틀(38px). 나머지는 보통 그리드.
4. **풀쿼트/콜아웃**: 본문 중 강조할 문단을 왼쪽 레드 보더 + 큰 인용부호로 강조. Confluence "정보 패널" 컨버터가 실제로 만들어낼 결과물과 자연스럽게 연결된다.
5. **시리즈 위젯**(연재물 전용): 벨로그 벤치마크. 연한 회색 패널 + 레드 책갈피 아이콘 + "목록 보기"로 펼치는 회차 목록 + "N화 · 최신/이전·다음 화살표". 이미지 히어로가 없는 연재 글에서 "이것도 시리즈의 일부"라는 존재감을 대신 만들어준다.

## 상단(헤더) 구성

2단 구조로, 화면별로 무게를 다르게 준다.

- **유틸리티 바** (얇고 조용함): 검색 아이콘. `--color-text-secondary` 톤으로 절제. 카테고리 퀵링크는 실제 카테고리 데이터가 아직 없어(data-spec.md에 필드 없음) 넣지 않았다 — [viewer-editorial-ui/spec.md](../tasks/viewer-editorial-ui/spec.md) Out of Scope 참고. 검색 자체는 2026-09-15 `@sfood/ui` 전면 도입 이후 `CommandPalette` 컴포넌트로 구현되어 있다([design-system-adoption.md](design-system-adoption.md) 참고). 검색 트리거 아이콘 자체는 라이브러리에 대응 컴포넌트가 없어 여전히 얇은 스트로크의 인라인 SVG를 직접 쓴다.
- **마스트헤드** (홈 화면에서만 크게): 굵은 워드마크 + 한 줄 태그라인("에쓰푸드 IT팀의 기술 기록") + 레드 룰. 신문 1면 상단처럼 확실한 존재감.
- **상세 페이지에서는 마스트헤드를 접는다**: 얇은 sticky 헤더(로고+뒤로가기+검색)만 남겨 본문 가독성을 방해하지 않는다. 마스트헤드는 홈의 전유물이다.
- **검색 화면도 마스트헤드와 같은 언어를 쓴다**: 초안은 그냥 박스 안에 입력창 하나뿐이라 "우리 사이트"라는 느낌이 없었다. 이제는 키커("SEARCH")+큰 제목("무엇을 찾고 계신가요?")+레드 룰로 마스트헤드를 그대로 반복하고, 입력창도 박스가 아니라 밑줄만 있는 큰 텍스트(포커스 시 레드)로 바꿔 "채워 넣는" 느낌을 준다. 입력창 아래 카테고리 칩(둘러보기)을 둬서 검색어가 없어도 탐색이 가능하게 했다.

## 홈/리스트 페이지 구성

1. 마스트헤드
2. 카테고리 필터(ChipGroup 패턴, velog처럼 항목별 개수를 함께 보여준다)
3. **히어로 카드**: 최신 글 1건. 사진 없이 레드 틴트 배경 패널+큰 타이틀로 무게를 준다(위 "이미지 없이도 성립하는 디자인인가" 참고)
4. **"최신 글" 그리드**: 키커+제목+2줄 요약+작성자/날짜의 **텍스트 전용 카드가 기본값**. 본문에 실제 이미지가 있는 글만 선택적으로 썸네일이 붙는다(벨로그와 동일 — 이미지 카드와 텍스트 카드가 같은 그리드에 자연스럽게 섞인다). 카드 자체는 `design-system.md`의 20px 라운드+3-layer 그림자 유지
5. **사이드바 "최근 댓글"**: 랭킹/조회수 리스트는 쓰지 않는다 — 우리 목적은 "경쟁"이 아니라 "공유와 전달"이므로 순위를 매기는 표현 자체를 배제한다(2026-09-14 결정, 초안에 있던 순번 랭킹 사이드바를 제거). 대신 최근 댓글(작성자+인용+어느 글인지)을 보여줘 "지금 지식이 오가고 있다"는 인상을 준다. 그리드 옆(데스크톱) 또는 그리드 다음(모바일)에 배치
6. 페이지네이션

## 상세(문서) 페이지 구성

1. 얇은 sticky 헤더(마스트헤드 없음)
2. 키커(카테고리) + 큰 제목(28px보다 크게, 32~36px) + 바이라인(이름+팀+날짜+예상 읽기 시간 — 아바타 이미지 없음, 아래 "아바타를 쓰지 않는 이유" 참고)
3. **히어로 이미지는 있을 때만**. 본문에 실제 이미지가 있는 글만 `.article-hero`를 쓴다 — 강제하지 않는다. **연재물은 이미지 자리에 시리즈 위젯**(진행률+회차 목록+이전/다음)을 대신 쓴다(위 "이미지 없이도 성립하는 디자인인가" 참고). 목업의 예시 글은 기술 글이라 이미지 없이 시리즈 위젯만 쓰는 경우를 보여준다.
4. 본문 — 읽기 폭 제한(약 680px), 줄간격 1.7~1.8. 첫 문단은 약간 크게(리드 문단) 처리해 진입감을 준다.
5. 풀쿼트/콜아웃(Confluence 정보 패널 변환 결과가 여기 해당)
6. **관련 글**: 썸네일 없이 키커+제목만 있는 텍스트 리스트(초안의 2열 썸네일 그리드를 텍스트 전용으로 변경 — 아래 참고)
7. **댓글**([design-benchmark.md](design-benchmark.md)의 Dribbble 벤치마킹 구조 그대로 — 이 페이지에만 존재, 목록 화면에는 없음). 상세 프로세스는 아래 "댓글 작성 프로세스" 참고.

### 아바타를 쓰지 않는 이유 (2026-09-14 결정)

이 서비스에는 회원가입/계정 개념이 없다 — MS 로그인은 그 순간 신원을 확인만 할 뿐 프로필을 만들지 않고, 외부 방문자는 매번 이름을 직접 입력한다. 즉 어디에도 "프로필 사진"이 존재할 수 없는 구조다. 초안에 있던 원형 회색 플레이스홀더(아바타 자리)는 실제로 채워질 값이 없는 장식이었으므로 전부 제거했다 — 게시글 바이라인, 댓글, "최근 댓글" 사이드바 전부 이름 텍스트만으로 작성자를 표시한다.

### 댓글 작성 프로세스 (2026-09-14 결정, 09-15 수정)

**초안(1차 수정)의 문제**: 이름/이메일 입력창·MS 인증 링크·댓글창을 전부 한 화면에 동시에 두고, 그 위에 "① 신원확인 ② 작성 ③ 등록"이라는 진행률 표시만 얹었다. 이건 **순서를 표시만 한 것**이지 실제로 화면이 순서에 맞게 바뀐 게 아니었다 — 로그인 전에도 댓글창이 이미 다 보이는 건 여전히 잘못된 구조였다.

**수정된 원칙**: 로그인/신원 확인 전에는 댓글 입력창 자체가 화면에 없다(로그인 전 댓글 작성을 막아두는 일반적인 서비스 패턴과 동일). 화면은 아래 3개의 서로 다른 카드 중 **한 번에 하나만** 보이며, 이전 카드는 완전히 사라진다(표시만 흐려지는 게 아니라 DOM에서 실제로 숨겨짐).

1. **게이트 화면** — 처음 진입 시 유일하게 보이는 것. "댓글을 남기려면 먼저 작성자를 확인해주세요"라는 안내와 두 개의 버튼(`MS 계정으로 인증 (사내 직원)` / `이름으로 계속하기 (외부 방문자)`)만 있다. 이름·이메일 입력창도, 댓글 입력창도 여기엔 없다.
2. **확인 화면** — 게이트에서 고른 방식에 해당하는 카드만 나타난다(다른 쪽 카드·게이트는 사라짐).
   - MS 선택 시: 먼저 "AX Auth로 이동 중…" 상태(실제로는 마이크로소프트 로그인으로 리다이렉트되는 왕복을 표현)를 잠깐 보여준 뒤, 인증이 끝나면 이메일이 검증되어 표시되고 이름은 제안값이 채워진 채로 여전히 고칠 수 있는 입력창으로 나타난다. "확인하고 댓글 작성" 버튼을 눌러야 다음 화면으로 넘어간다.
   - 외부 방문자 선택 시: 이름·이메일 입력창이 나타난다. 비어 있는 채로 "확인하고 댓글 작성"을 누르면 통과하지 못하고 무엇이 빠졌는지 안내한다.
3. **작성 화면** — 확인이 끝나야만 나타난다. 상단에 "홍길동 · 외부 방문자 [다른 사용자로]" 같은 확정된 신원 한 줄과, 그 아래 댓글 입력창+등록 버튼만 있다. 등록을 누르면 댓글이 목록 맨 위에 즉시 추가되고 "댓글 N개"가 올라간다. 신원은 유지되므로 이어서 댓글을 더 남길 때는 다시 게이트로 돌아가지 않는다("다른 사용자로"를 누르면 게이트로 되돌아갈 수 있다).

이 흐름은 [mockups/blog-editorial-direction.html](mockups/blog-editorial-direction.html) 정적 목업에 먼저 구현됐다(MS 인증은 900ms 지연으로 흉내냄) — 화면 전환이 더미 애니메이션이 아니라 실제로 이전 단계의 DOM 요소가 사라지는 방식이었다. 2026-09-15 [src/components/comments/CommentSection.tsx](../../src/components/comments/CommentSection.tsx)로 실제 구현되면서, MS 인증은 진짜 AX Auth 리다이렉트로, 게이트/확인 단계는 `@sfood/ui`의 `Card`/`Button`/`Input`/`ColorTag`로, 신원 확인 후 목록·작성창은 `CommentThread`로 교체됐다 — 단계 전환 로직(한 번에 하나만 실제로 렌더링)은 목업의 원칙 그대로다.

## "AI 슬롭(AI Slop)" 안티패턴 점검 (2026-09-15)

[925studios의 AI Slop Web Design 가이드](https://www.925studios.co/blog/ai-slop-web-design-guide)를 기준으로 목업을 다시 점검했다. 이 글이 정의하는 "AI 슬롭"은 AI 툴이 기본값을 그대로 둬서 생기는, 브랜드와 무관한 장식(Inter 폰트, 보라-파랑 그라데이션, 균일한 카드, 반응 없는 호버 등)이다. 실제로 우리 목업에 2가지가 남아있었다.

- **장식용 그라데이션**: `.post-thumb`(핑크-오렌지)와 `.article-hero`(핑크-레드)에 아무 의미 없는 그라데이션이 남아 있었다. 지난 턴에 "이미지는 있으면 보너스"로 정책을 바꿔놓고도, 시각적으로는 여전히 "사진인 척하는 색깔 블록"을 쓰고 있었던 것 — 가이드가 지적하는 "플레이스홀더를 그대로 둔 채 배포하는" 패턴과 정확히 같다. **중립 회색(`--surface-muted`) + 아웃라인 이미지 아이콘**으로 바꿨다. 실제 이미지가 있으면 그 자리를 대체하고, 없으면 "여기에 이미지가 들어갈 수 있다"는 것만 정직하게 보여준다.
- **반응 없는 호버(Missing Micro-Interactions)**: 클릭 가능한 `.post-card`, `.hero`, `.recent-item`(사이드바)에 호버 상태가 전혀 없었다. `post-card`는 살짝 떠오르며 제목이 레드로, `hero`는 왼쪽 레드 보더가 두꺼워지며, `recent-item`은 인용문이 레드로 바뀌도록 추가했다.

이미 잘 지키고 있던 것도 확인했다 — Pretendard/맑은고딕(Inter 기본값 아님), 의미 기반 CSS 변수명(`--text-primary`/`--brand-red` 등 장식적 이름이 아님), 라운드 스케일이 8/14/20/32px로 컴포넌트별 의도가 있음(전부 16px 균일이 아님), 카피가 구체적임("Build the future" 같은 모호한 문구 없음). 앞으로 이 목업에 새 화면을 추가할 때는 이 체크리스트(그라데이션 장식·균일한 크기·반응 없는 호버·모호한 카피)를 한 번씩 다시 대조한다.

## 하단(푸터) 구성

- 푸터 바로 위에 **옅은 레드 틴트 배경의 콜아웃 밴드**를 하나 둔다(뉴스레터 구독/새 글 알림 같은 문구) — 마스트헤드의 "레드 룰"과 짝을 이루는 하단 북엔드.
- 그 아래는 조용한 실제 푸터: 로고+한 줄 소개, 링크 컬럼(회사소개/관련 사이트/RSS), 저작권. 마스트헤드가 화려한 만큼 푸터는 절제해서 "시작은 강하게, 끝은 담백하게" 리듬을 만든다.
